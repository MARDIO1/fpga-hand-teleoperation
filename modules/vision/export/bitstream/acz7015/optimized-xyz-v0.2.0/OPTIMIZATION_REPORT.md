# 无软件限速实测、异步预览与硬件资源报告

日期：2026-10-27（北京时间）。设备：ACZ7015，xc7z015clg485-2，PL 100 MHz。

## 结果

当前配置的供帧速度约 30 fps。去掉软件限速后，仅点输出实测 **29.56 fps**；开启最高 2 Hz 的异步同帧预览后实测 **28.62 fps**。预览的整图读取、打包和文件发布已移出识别主线程，但仍会竞争 PS/DDR，尚未做到预览零影响。

|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 仅点 | 600 | 29.564 | 33.825 | 35.247 | 65.956 | 600 | 0 | 0 | 0 |
| 异步预览，最高 2 Hz | 600 | 28.620 | 34.941 | 34.407 | 66.585 | 600 | 42 | 0 | 0 |

统计剔除前 3 帧，吞吐取连续完成时间戳间隔，包含循环间的调度、统计和打印开销；不是局部计时均值的倒数。后台进程先完成初始化，再开始采集。相机计数器实测分别 29.933/29.956 Hz。

旧测试汇总中的 `completed_hz=1000/mean(cycle_ms)` 没有计入循环外开销，不能当作完整输出上限。例如最终仅点局部倒数为 30.416 Hz，而连续完成时刻测得 29.564 Hz；本报告采用后者。逐帧 JSON 保留旧字段用于追溯，以 `steady_wall_completed_hz` 为准。

“发布队列丢弃为 0”不表示相机每个源帧都被处理。预览仍使处理吞吐低于源帧率；当前采集控制并非无损连续录像，也没有证明相机两眼曝光同步。本轮实时场景最终仅点匹配 0–2 对，预览匹配 1–2 对，不能将此次吞吐视为任意复杂场景的最坏情况保证。

## 软件改动与部署

- 新增独立发布进程，输入队列最多保留 1 个待处理任务；慢客户端或慢写入不会形成无限队列。队列满时跳过该次发布并计数；退出时保存最终点表。
- 使用硬件原已允许的三个槽 `0x1e000000/0x1e200000/0x1e600000`，没有新增物理地址。提交预览时先建立软件读引用，再释放硬件租约；后台完成 CPU 副本后回传 ACK，此前采集不得覆盖该槽。
- 主线程在另外两个可用槽上采集和识别；槽选择和后台状态检查提前到等待采集之前，避免在 EOF/SOF 交界处延迟重新启动采集。
- 点表、预览仍使用原子替换；每份预览携带自己的点表、帧号和时间戳，后台进程不把旧图叠加最新点表。
- `--fps 0` 关闭软件限速，默认仍为 30。默认输出 `/dev/shm/marker_results_v2`，避免高频写板载存储。完整周期统计改用连续完成时刻，并公开发布数和队列丢弃数。

已更新本目录上级 `software/marker_ingress_v2/run_direct_board.py` 与 `software/hls_markers/process_publisher.py`，以及板端同名软件。板端目录：`/home/xilinx/overlays/pl_stereo_hdmi/compact_optimized_20261027`。原入口备份为 `run_direct_board.py.before_async`。

原 `release/`、ZIP、SHA256SUMS 是历史冻结发布包，本轮未重打包，也未覆盖其软件副本；不要误将它当作新版异步软件。此次没有重新综合、更新 bit/HWH 或改动阈值、标定和识别算法。

板端运行命令（同一时刻只允许一个采集控制程序）：

sudo python3 software/marker_ingress_v2/run_direct_board.py --frames 0 --fps 0 --snapshot-fps 2

**资源优化首选几何模块**：它占已用 LUT 的 64.7%、已用 FF 的 56.8%、DSP 的 87.5%。当前几何输入／输出使用 float64；后续可建立独立候选，评估 float32／分段定点、运算单元复用及精简通用矩阵运算，再以像素和毫米误差门限验收。本轮未更改精度或几何硬件。

**BRAM 优化首选颜色／连通域**：占 16/37 个 BRAM36 等效。应检查标签表、区域表与 FIFO 实际峰值后再缩减，不能仅凭典型场景减少容量。

100 MHz 已约束路径 setup WNS +0.898 ns、hold WHS +0.047 ns；原报告仍有相机时钟未完整约束、660 个未约束内部端点、输入／输出延迟缺失等问题。因此这里不能宣称全设计所有路径时序通过，也不建议依据这两个正裕量直接升频。

主识别进程 CPU 约为单核的 55.7%／53.4%（仅点／预览），不含后台发布子进程；没有将它冒充整个 PS 的总 CPU 或功耗。

- 3 项独立进程回归通过：慢发布下有界队列与最终点表、后台写入失败传播、预览槽在复制 ACK 前不得复用。
- 600 帧仅点和 600 帧最终预览通过；600 份点表均已发布，预览包帧号与该帧点表一致。

- `runner_smoke.json`：实际入口额外运行 60 帧，正常退出，最终点表序号 59，预览可解析。
- 最终 overlay 保持加载，bit SHA256 `74ee06b4e08f151b79a6a98472a7055930393c830b0127d5c14a28547e0e9418`；控制器 status `0x2`、error `0x0`，无忙读、采集或租约；结果 DMA idle，采集 VDMA halted。测试程序已退出，未留下后台常驻识别服务。

过程中的线程发布、进程仅写文件、槽选择在 EOF 后执行等候选均未作为最终成果；原始结果保留在 results 下。同步预览内存目录对照约 27.67 Hz（局部计时口径），历史图中预览为 21.32 Hz（含 30 Hz 限速、板载目录）；场景和统计口径不同，不将这些数据包装成严格同场景加速比。

后续帧率方向：先减少预览引起的 DDR／CPU 竞争并检查采集启动窗口；若要超过当前约 30 fps 的新帧输出，必须先提升相机实际供帧速度。尚未进行长期、温度、复杂密集标记场景或绝对三维精度验收。
